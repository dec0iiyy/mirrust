# Releasing mirrust

For the maintainer. A release is a tag: pushing `vX.Y.Z` runs
[`.github/workflows/release.yml`](../.github/workflows/release.yml), which builds the binary
for five targets, tests it, and publishes a GitHub Release that a user can download with one
command. Nothing is built on your machine.

**Status: no release has been published yet, and the workflow has not run.** It was checked
with `actionlint`, and its shell steps were run locally on macOS (see
[What has not been exercised](#what-has-not-been-exercised)). Do a dry run (below) before the
first tag.

## What a release contains

For a tag `v0.2.0` the release holds eleven files and `SHA256SUMS`:

| File | What it is |
| --- | --- |
| `mirrust-linux-x86_64`, `mirrust-linux-aarch64`, `mirrust-macos-arm64`, `mirrust-macos-x86_64`, `mirrust-windows-x86_64.exe` | The bare binary, what a one-line `curl -o` download fetches. The Unix ones need `chmod +x`. |
| `mirrust-v0.2.0-<target>.tar.gz` (four, Linux and macOS) | The same binary with `LICENSE`, `NOTICE`, `README.md` and `deploy/mirrust.service`, under a directory of the same name. |
| `mirrust-v0.2.0-x86_64-pc-windows-msvc.zip` | `mirrust.exe` with `LICENSE`, `NOTICE` and `README.md`, under a directory of the same name. No `mirrust.service`: it is a systemd unit. |
| `install.sh` | The installer, copied from the tagged commit by the `SHA256SUMS` job. `curl -fsSL https://github.com/dec0iiyy/mirrust/releases/latest/download/install.sh \| sh` downloads the binary for the system, checks it against `SHA256SUMS` and installs it. Release 0.1.0 does not have it; the first release after it does. |
| `SHA256SUMS` | The SHA-256 of the eleven files above, in the format of `sha256sum -c`. |

The release notes are generated by GitHub from the merged pull requests and commits since
the previous tag, below a short "Verify the download" section written by the workflow.

## Targets

| Target | Runner | Binary | Needs to run |
| --- | --- | --- | --- |
| `x86_64-unknown-linux-musl` | `ubuntu-24.04` | `mirrust-linux-x86_64` | Linux on x86_64. Static: no glibc, no shared library, any distribution. |
| `aarch64-unknown-linux-musl` | `ubuntu-24.04-arm` | `mirrust-linux-aarch64` | Linux on arm64. Static, as above. |
| `aarch64-apple-darwin` | `macos-latest` | `mirrust-macos-arm64` | macOS on Apple silicon. |
| `x86_64-apple-darwin` | `macos-latest` (cross-compiled) | `mirrust-macos-x86_64` | macOS on Intel, or on Apple silicon with Rosetta 2. |
| `x86_64-pc-windows-msvc` | `windows-latest` | `mirrust-windows-x86_64.exe` | Windows on x86_64. **Not run yet**, see below. For local testing only. |

Notes:

- The Linux binaries are linked against musl, so they do not depend on the glibc of the
  machine. The cost is musl's memory allocator, which is slower than glibc's under heavy
  multi-threaded load; that was not measured for mirrust.
- The build compiles `aws-lc-sys` (a dependency of rustls and quinn) with `musl-gcc` from the
  `musl-tools` package: the workflow sets `CC_<target>=musl-gcc`, because otherwise the `cc`
  crate looks for a cross compiler named `x86_64-linux-musl-gcc`. The crate has
  pregenerated bindings for both musl targets, so CMake and bindgen are not needed.
- The Windows build is for local testing: the systemd unit and TCP SYN capture do not
  apply there, so the TCP checks show as not measured, as on every platform for now. It
  has not been built or run yet, on a runner or anywhere else. `aws-lc-sys` needs NASM on
  Windows x86-64; the workflow does not install it but sets `AWS_LC_SYS_PREBUILT_NASM=1`,
  which makes the crate use the object files it ships (the same setting as in `ci.yml`).
  aarch64 Windows is not built. The binary is not signed, so Windows SmartScreen may warn
  about a file downloaded in a browser.
- The macOS binaries are not signed or notarized. A file fetched with `curl` runs; a file
  downloaded in a browser carries the quarantine flag, and Gatekeeper refuses it until
  `xattr -d com.apple.quarantine FILE`.
- The build uses the current stable Rust and no build cache, so that every release is built
  from scratch. The MSRV (1.88) is checked by CI, not by the release.
- **Fallback if musl does not work.** If a musl build fails and cannot be fixed, build that
  target for glibc instead: in the matrix of `release.yml` use `x86_64-unknown-linux-gnu` on
  `ubuntu-22.04` (and `aarch64-unknown-linux-gnu` on `ubuntu-22.04-arm`), delete the
  `musl-tools` and "binary is static" steps, and drop `alpine:3` from the smoke test. A binary
  built on Ubuntu 22.04 needs glibc 2.35 or later (Debian 12, Ubuntu 22.04 or newer). Keep the
  asset names, so that download links do not change. No fallback has been needed so far,
  because nothing has been built yet.
- The Docker image in `deploy/Dockerfile` is not part of the release workflow.

## How to cut a release

1. **Bump the version.** Set `version` in `crates/server/Cargo.toml`, the `server` package
   that holds the `mirrust` binary. The workflow compares the tag with this value and only
   this one: the other crates have their own versions and are not published. Update the
   version that the README states (the "Status" section) if it names one.
2. **Update the lock file and check the build:**

   ```console
   $ cargo build --release --locked --bin mirrust
   ```

   A version change also changes `Cargo.lock`. If `--locked` reports that the lock file needs
   an update, run `cargo check` once and commit the result: the release builds use `--locked`
   and fail on a stale lock file.
3. **Commit and push to `main`, and wait for CI** (`ci.yml`) to pass.
4. **Dry run** (first release, and after every change to `release.yml`):

   ```console
   $ gh workflow run release.yml -f publish=false
   $ gh run watch
   ```

   `gh workflow run` takes the workflow file from the default branch, so `release.yml` must
   be on `main` first; add `--ref BRANCH` to try a branch that has it. A dry run builds, tests and checksums exactly
   as a release does, skips the tag check and the last job, and names the files after the
   commit (`mirrust-dev-<sha7>-<target>.tar.gz`). The files stay as workflow artifacts for 7
   days: open the run in the Actions tab, or

   ```console
   $ gh run download RUN_ID --name release-files --dir dryrun
   $ cd dryrun && sha256sum -c SHA256SUMS
   ```

   `release-files` holds all eleven files and `SHA256SUMS`; the five `dist-<target>` artifacts
   hold one target each.
5. **Tag and push the tag:**

   ```console
   $ git tag -a v0.2.0 -m "mirrust 0.2.0"
   $ git push origin v0.2.0
   ```

   The tag name is `v` plus the version from step 1. A tag with a hyphen, such as
   `v0.2.0-rc.1`, becomes a pre-release (the version in Cargo.toml must then be
   `0.2.0-rc.1`).
6. **Watch the run** (`gh run watch`), then open the release on GitHub and read the notes.
   If you want to edit them, do it in the web page or with `gh release edit`.

### What the workflow does

1. `version check`: reads the version of the `server` package with `cargo metadata` and
   fails unless the tag is `v` plus that version. Nothing else starts before it passes.
2. `build` (five jobs in parallel): installs Rust and the target; on Linux installs
   `musl-tools` and points the C compiler at `musl-gcc`; builds with
   `cargo build --release --locked --bin mirrust --target T`; for Linux checks that the
   binary has no dynamic loader and no shared-library dependency; runs the smoke test; makes
   the `.tar.gz` (the `.zip` on Windows, made with 7-Zip) and the bare binary; uploads them.
   - The Linux smoke test (`.github/scripts/smoke-test-linux.sh`) starts a clean
     `debian:12-slim` and a clean `alpine:3` container for the binary of that runner's
     architecture, mounts the binary read-only, and runs `mirrust --help`; then it starts
     mirrust on port 8443 inside the container, fetches `/api/clean` over HTTPS with curl
     (the certificate is self-signed, so `-k`; curl is installed in the throwaway container),
     and requires HTTP/2, a live server process and an `audit` field in the answer.
   - On macOS the same script (`.github/scripts/smoke-test.sh`) runs on the runner. On
     Windows its PowerShell counterpart (`.github/scripts/smoke-test.ps1`) does: `--help`,
     then `mirrust.exe` in the background on port 8443, `curl.exe -k` for `/api/clean` with
     the same checks, and `Stop-Process` at the end.
   - A failing smoke test fails the job and so the release.
3. `SHA256SUMS`: checks out the tagged commit, downloads the files of all five jobs, requires
   exactly ten, copies `install.sh` from the checkout next to them (mode 0755) and requires
   eleven, writes `SHA256SUMS` with `sha256sum`, checks it, and uploads everything as `release-files`.
4. `publish release` (tag pushes, and manual runs with `publish=true` on a tag): the only
   job with write access (`contents: write`, plus `id-token: write` and `attestations: write`
   for the attestation). It downloads `release-files`, attests the build provenance of every
   file in `SHA256SUMS` with `actions/attest-build-provenance`, and runs `gh release create
   --verify-tag --generate-notes` with all twelve files. The rest of the workflow has read-only
   permissions.

To publish from a manual run, choose the tag under "Use workflow from" (or `gh workflow run
release.yml --ref v0.2.0 -f publish=true`). A manual run with `publish=true` on a branch
fails in the first job.

### If a run fails

- **Version check:** the tag and `crates/server/Cargo.toml` disagree. No release exists, so
  delete the tag (`git push origin :refs/tags/v0.2.0`, `git tag -d v0.2.0`), fix the
  version, commit, and tag again.
- **A build or smoke-test job:** nothing was published. Fix the cause on `main`, delete the
  tag as above and tag the new commit. "Re-run failed jobs" on the old run builds the old
  commit again, which helps only for a runner or network failure.
- **Publish job:** the release is created as the last step, with the files attached by the
  same command. If it failed before that, "Re-run failed jobs" works. If a release was
  created but is wrong, delete it with `gh release delete v0.2.0 --cleanup-tag` and start
  again with a new tag; do not move a tag that users may have seen.

## Verify a download

Download the file and `SHA256SUMS` from the release page, then check that file:

```console
$ curl -fLO https://github.com/dec0iiyy/mirrust/releases/download/v0.2.0/mirrust-linux-x86_64
$ curl -fLO https://github.com/dec0iiyy/mirrust/releases/download/v0.2.0/SHA256SUMS
$ grep ' mirrust-linux-x86_64$' SHA256SUMS | sha256sum -c -
mirrust-linux-x86_64: OK
```

On macOS, use `shasum -a 256 -c -` in place of `sha256sum -c -`. The checksum file proves that
the download is intact. It does not prove where the file came from, because it is fetched from
the same place.

The attestation does: it is a signature, made by the release workflow with GitHub's OIDC
identity and stored by GitHub, that this repository's workflow built a file with exactly this
digest. With the [GitHub CLI](https://cli.github.com/):

```console
$ gh attestation verify mirrust-linux-x86_64 --repo dec0iiyy/mirrust
```

To insist on this workflow and not any workflow of the repository, add
`--signer-workflow dec0iiyy/mirrust/.github/workflows/release.yml`. The same works for the
archives. The action is `actions/attest-build-provenance` v4, pinned by commit in the
workflow, which since version 4 is a thin wrapper around `actions/attest`.

## What has been exercised

Release 0.1.0 was published by this workflow on 2026-11-20, after a dry run
(`publish=false`) that built and smoke-tested every target. On GitHub's runners:

- All five builds, including both musl builds (`musl-tools` with `CC_<target>=musl-gcc`) and the
  Windows build with `AWS_LC_SYS_PREBUILT_NASM=1`, and the Linux "binary is static" check.
- The smoke tests: the Linux binaries in clean `debian:12-slim` and `alpine:3` containers, the
  macOS binaries on the runner (the x86_64 one included) and `mirrust.exe` on the Windows
  runner. On Windows, `curl.exe` negotiated HTTP/1.1, so that smoke test accepts HTTP/1.1 or
  HTTP/2.
- The version check, the packaging, `SHA256SUMS` over ten files (release 0.1.0 predates `install.sh`), `gh release create` and the
  build provenance attestation.

By hand, from the published release: the one-line download of `mirrust-macos-arm64` from
`releases/latest/download/`, `shasum -a 256 -c` against `SHA256SUMS`, `gh attestation verify
mirrust --repo dec0iiyy/mirrust` (exit code 0), and `mirrust --help` from the downloaded file.
`SHA256SUMS` itself carries no attestation, only the files it lists do.

## What has not been exercised

- A musl build of mirrust under `deploy/mirrust.service` (the sandbox, and
  `SystemCallFilter=@system-service` in particular) or on a real server. The binary that
  the docs say has been run under the unit was built for glibc on Ubuntu 24.04.
- The Linux and Windows binaries on real machines other than the CI runners and containers
  above; the Windows binary has only run its smoke test on the runner.
- The macOS binaries after a browser download: they are not signed or notarised, so
  Gatekeeper may stop them (see the macOS note above).
- The one-line downloads for the other platforms, and the checksum and attestation checks for
  files other than `mirrust-macos-arm64`.
- The step that adds `install.sh` to the release (checkout, copy, the count of eleven) has not
  run on a runner. Because the attestation is made from `SHA256SUMS`, which lists `install.sh`,
  the installer is attested like the binaries, but that has not been seen either. After the
  first release that carries it, run
  `curl -fsSL https://github.com/dec0iiyy/mirrust/releases/latest/download/install.sh | sh -s -- --prefix DIR`
  once and `gh attestation verify install.sh --repo dec0iiyy/mirrust` on the downloaded file.
  `.github/scripts/test-install.sh --online` tests the installer against a published release
  by hand; CI runs only its tests that need no network.
